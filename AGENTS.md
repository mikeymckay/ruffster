# Development conventions

- Keep the product transparent and local-first. Never add screenshot, keystroke, microphone, camera, message-content or full-URL collection.
- Do not install or enable background services on a user's machine without an explicit installation action and clear disclosure. Avoid claims of tamper detection or complete coverage.
- Build small independently verifiable milestones; use standard-library Python where practical, automated tests, and real-device checks. Document what was tested and what remains unverified.
- Prioritize student-facing platforms in this order: macOS, then Windows. Linux is a development/test host only unless the product scope changes; do not build Linux student features by default. Isolate OS adapters, and never treat a Linux host as evidence of macOS behavior.
- Lifecycle decision: macOS uses a per-user `launchd` agent. The Windows prototype uses an interactive per-user Task Scheduler logon task because foreground-app observation and the visible tray indicator belong in the signed-in desktop session; do not move collection into a hidden Session 0 service. Revisit a service only with a separate, disclosed session agent and narrowly scoped IPC.
- On macOS, the agent starts the visible status companion before collection and waits for its `READY` response. After each successfully stored sample, it writes a `HEARTBEAT` line to the companion. On Windows, the agent starts the visible tray companion through a per-run readiness event; after each successfully stored sample it signals a separate auto-reset heartbeat event. Both indicators show starting, on, and paused states from heartbeat freshness, and collection stops if the helper or its heartbeat channel disappears. Preserve this ordering and fail-closed behavior when changing startup or IPC.
- Store timestamps in UTC. Treat missing observations as uncertainty, preserve distinctions between measured and estimated data, and avoid inferring intent.
- Keep SQLite data local, minimize collection, provide retention and deletion before deployment, and document schema and permissions as they evolve.
- The dashboard must bind to loopback by default; review local access and cross-origin risks before adding mutation endpoints or distribution.
- Design parent reports for a nontechnical first read: lead with clearly labeled weekly and school-hours observations, keep estimates distinct from measured counters, and put secondary technical detail behind keyboard-accessible disclosures. Do not hide limitations or uncertainty to make the report appear simpler.
- Empty report sections must describe the observation that is missing without implying zero use or uninterrupted monitoring. State when the data cannot establish whether an app or website was used.
- Parent-to-child key handoff uses a separate, explicitly started local-network listener with a short lifetime, one-use bearer token, and exact certificate pin. The visible two-digit code only selects a nearby sender through local UDP discovery; it is not authentication, and the short internal endpoint is exchanged on the local network. The pinned TLS transfer sends only the typed public key; never the parent vault or private key. Stop the listener after use, expiry, explicit parent lock, or app shutdown. This prototype protocol is not independently reviewed and is not persistent pairing.
- Parent-facing conversation prompts must be tied to an observed fact or missing observation, describe what the data cannot establish, and avoid classifying a child's behavior or inferring intent.
- Public README and website copy must distinguish implemented behavior from plans, use synthetic-only screenshots, state preview readiness plainly, and avoid download links until a supported signed release exists.
- Keep the static GitHub Pages source dependency-free at runtime. Run `npm ci && npm run check:pages-a11y` when changing its pages; this pinned local axe-core check also runs in CI and covers desktop and phone viewports. Automated checks complement, but do not replace, keyboard and screen-reader review.
- Keep signing identities, notarization credentials, private keys, and keychain exports out of source control, logs, screenshots, and validation artifacts. Signing and notarization claims require a successful native macOS run; a packaging script or CI build alone is not evidence of acceptance.
- Keep real device names, account names, home-directory paths, public or tailnet addresses, and family-network subnets out of tracked documentation and validation artifacts. Use generic test-device labels and documentation-only network ranges.
