# Product direction: a family-first experience

Status: product direction with a published Mac family release. Ruffster is intended for ongoing, visible use by families. The app includes encrypted activity reports, a local parent dashboard, and a guided but unsigned Mac setup app. The release package has been verified on Apple silicon, but the first family setup, two-Mac report flow, and routine updates still need hands-on use. Windows setup is implemented but has not been tried on a family Windows computer.

## The family journey

1. **Understand before installing.** A plain-language page explains what is collected, where it stays, what is not collected, the child's visible indicator, and the limits of reports. Show example screens with invented data clearly marked as examples. No account or school involvement is required.
2. **Set up together.** The parent downloads Ruffster for Mac and installs it on the parent and child computers. A short welcome screen explains what Ruffster records and offers distinct actions to open the parent dashboard or set up the child's computer. The family reviews the collection choices together and keeps the visible status indicator in view. Add pictures for any operating-system permission that is confusing.
3. **Choose minimal defaults.** Begin with app usage and monitoring coverage, with short, explicit retention and an editable school schedule. Website domain collection is optional and currently experimental. It requires an extension on the child's computer, works only in supported browsers while enabled, and can be bypassed by switching browsers or disabling it. Treat it as an optional extra, never as complete website monitoring; keep it out of the standard setup until installation, status, and coverage are understandable. Network classification is user-labeled; do not infer that an unfamiliar network is school. Explain that network totals are device/interface-level, not website traffic. Defaults require user research and privacy review before release.
4. **Set up parent access and connect simply.** New parent setups use a six-digit PIN that only the parent should know. It keeps access private from the child, but is not strong protection if someone copies the recovery file and guesses PINs offline; explain that in plain language without leading with hacker threats. Older recovery copies retain their original phrase. The child device receives only what it needs to encrypt observations; it cannot use that to open reports. Use the same easy pattern whenever information moves between computers: the sender shows two digits, and the receiver enters them. For setup the parent sends; for a report the child sends. Keep both on the same Wi-Fi and the parent's PIN on the parent's computer. The digits only find the nearby computer; they are not a password. The actual transfer is protected and carries only a public key or already-encrypted report. Validate local network behavior on supported Macs and Windows before family distribution.
5. **Verify together.** The wizard confirms the status indicator is visible, shows a small live sample and explains collection delays, missing permissions, sleep, and limitations. Offer to discard setup data. A parent can open a dashboard on the paired device; locally viewing sensitive reports requires parent authentication. Without a paired device, a parent can use a deliberately designed same-device unlock flow; do not pretend the child computer never sees decrypted data during that flow.
6. **Everyday use.** The child sees a clear menu-bar/system-tray status, what is collected and where it goes, plus an honest unavailable state if monitoring or reporting is interrupted. Parent sees a calm daily/weekly overview, coverage, activity summaries, and network totals. Missing data stays missing; changes and gaps are not treated as misconduct. Use conversational prompts and acknowledge shared devices, schoolwork, background traffic, and ambiguous categories. Show website coverage as “observed in Chrome” or “not available,” never imply that missing domains mean no browsing or suspicious activity. Do not send detailed notifications to a lock screen.
7. **Changes and exit.** A parent can change schedule, retention, pairing, and optional sources in settings; changes are visible to the child. Provide export, immediate deletion, key revocation, uninstall and understandable consequences. Explain that already-exported backups cannot be recalled, and clarify limitations of secure deletion on SSDs and backups.

## Design iterations

### Connecting parent and child devices

The current family app assumes both computers can connect directly over the same LAN. The two-digit code helps the computers find each other; the report transfer is encrypted. Keep encrypted report-file export/import as the fallback. Do not ask families to change router or firewall security settings.

An optional cloud rendezvous service is a later usability improvement: both apps make outbound connections to exchange a short-lived session identifier and connection candidates, then attempt a direct LAN connection. The service should never receive report contents or the parent private key. Rendezvous cannot overcome client isolation, blocked peer traffic, or networks that do not permit a direct path; in those cases use the file workflow. A future data-relay fallback is a separate feature requiring explicit opt-in and retention, cost, abuse, and privacy design. Use rate limits and short expirations because a two-digit selector has very little entropy. Keep this cloud service optional and avoid creating a cloud account requirement.

A default-off experimental macOS process traffic summary is available using `nettop` process labels and byte counters. It does not collect endpoints and cannot identify websites. Helpers may own connections, and short-lived processes or initial baselines can be missed. Keep it opt-in and clearly separate from website measurements.

Do not add compression to direct LAN transfer. Revisit compression only if a future server-relay feature makes bandwidth or temporary storage a concern; then measure representative reports and compress before any outer encryption. Activity rows are already individually encrypted, so measure actual package sizes rather than assume compression will help.

- **V1: dashboard on the child's machine with a parent password.** Easy to set up, but the computer must decrypt data when viewed; a password alone does not make data safe from a privileged or compromised machine. It also leaves parents dependent on physical access.
- **V2: pair a parent's device, keep the private key there, and encrypt observations to its public key.** Better parent-only access to stored reports and a more natural dashboard. The child device still sees observations before encryption and metadata may remain; protect transport and local temporary data. Parent device availability, recovery and data synchronization add complexity.
- **Recommended direction: V2, with a local-first incremental rollout.** Provide an explicitly explained same-device option if user research establishes its need; make separate-device viewing a first-class capability. No required cloud account. Remote access beyond the home requires a separately designed secure transport or optional end-to-end encrypted relay, not port forwarding instructions for families. Work offline and indicate when reports last synced.

The parent report offers context questions when it shows incomplete sessions, unobserved intervals, unlabeled routers, or unavailable/proxy/VPN configuration indicators. It says these observations do not classify behavior. Review the prompts with families and improve them based on what helps parents and children talk constructively.

## Encryption model to validate

Use established, independently reviewed cryptographic libraries and a documented threat model, not custom cryptography. The collection process encrypts records to a parent-controlled public key using an authenticated hybrid encryption design with fresh content keys. Parent private keys stay on paired parent devices and are protected by OS credential storage and user authentication where available. On-device observation plaintext exists in process memory before encryption; avoid persisting plaintext, logs, temporary files, SQLite sidecars or indexes containing sensitive details. Specify encrypted retention, integrity, replay protection, corruption handling, key rotation and recovery before implementation. Minimize or explicitly disclose unencrypted metadata. The system cannot protect observations against a compromised or privileged child's machine or guarantee availability against an administrator.

Local OS key storage alone is not the requested parent-only separation: Windows DPAPI commonly protects to the user or machine account; a child account's secrets are not automatically a parent's secrets. Separate-parent authentication and key custody matter. Full-disk encryption is useful defense in depth but is not a replacement for a parent-controlled key.

## Platform architecture

A shared core handles schemas, scheduling, encrypted records, reports, retention and tests. Per-user native components gather only supported observations and provide visible status. macOS needs an interactive-session agent and signed/notarized installer. Windows needs a per-user interactive component alongside any justified service; Windows services cannot directly interact with the desktop. Investigate session changes, sleep, permissions, user switching, restarts, and signed installation on actual devices. Avoid privileged services unless necessary. Browser extensions use the least permission necessary and record domains only after opt-in.

## Staged delivery and acceptance

1. **Research and threat model (open):** interview families; document the privacy boundary, supported OS versions, accessibility, offline behavior, key recovery and explicit non-goals. Validate setup and dashboard with nontechnical parents and children.
2. **Mac family release (published):** visible status, per-user launchd lifecycle, foreground app observations, interface totals, monitoring coverage, encrypted local records, and parent reports are implemented. The Apple-silicon download and disk image have been verified, but the package has not yet been installed for a family's first-run setup. Review setup windows, VoiceOver, sleep/wake, login, restarts, report sharing, and removal on the family's three Macs.
3. **Parent access and pairing (implemented; real-family flow open):** new parent access uses a six-digit PIN the child does not know, and older recovery copies remain readable. New setup and report transfer use a temporary two-digit nearby-computer selector and encrypted local transfer; the selector is not the report key. Mac-to-Mac discovery, network permissions, fallback behavior, and report recovery still need to be tried in the intended family flow. No parent PIN is sent to the child's computer. Independent review remains part of longer-term quality work.
4. **Windows vertical slice (early, unverified):** adapters, tray source and per-user Task Scheduler commands exist. The tray now reflects fresh completed-sample heartbeats and shows a paused state when observations become overdue; it stops collecting if the helper or heartbeat channel disappears. Compile, install, restart, visible state, and removal must still be checked on actual Windows machines and accounts. No claims from mocks alone.
5. **Family experience (in progress):** make installation and updates simpler, try pairing and recovery on real family Macs, finish accessibility review, improve help based on family use, and continue privacy review. A signed installer can make first launch and updates smoother, but does not replace these usability checks.
6. **Optional features (partial):** domain-only browser collection and static broad website-category hints exist experimentally; filtering guidance is advisory. The extension runs on the child's computer and can be disabled or bypassed using another browser, so it cannot provide complete web history and should remain opt-in and outside the standard installer for now. Validate browser behavior and category quality with families. Never present site-level traffic estimates as measurements.

Current code has encrypted reports, parent PIN access, child-visible status, setup and removal paths, app and network observations, a dashboard, and recovery from an encrypted parent copy. It still needs real family setup and report-sharing checks, interactive accessibility review, Windows validation on a Windows computer, and review of data deletion across all saved copies. Browser categories are a small hand-maintained mapping from hostnames; unknown sites remain uncategorized, and a category is not a judgment about the child or activity.
