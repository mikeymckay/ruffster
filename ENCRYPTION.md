# Encryption work in progress

The monitoring agent now refuses to start without a parent public key and writes activity only as encrypted SQLite events. Older prototype runs and lower-level development storage helpers can still produce plaintext databases; the dashboard retains compatibility for opening those files, and this change does not migrate or erase existing data. A parent-side dashboard can open a copied encrypted database using the parent private key and reconstruct reports in an in-memory SQLite database. Experimental one-time pinned-TLS transfer can move an encrypted report or the typed public key over the local network; this is not persistent pairing, and there is no OS-integrated parent-key custody. The local transfer UI now uses a two-digit nearby-device selector, resolved to the existing TLS code by a short-lived UDP listener. The two digits are not authentication: anyone on the same local network can try all values or observe a matching response. Reports remain encrypted to the parent's private key, which is never transferred. New parent vaults use a six-digit PIN. It is intended to keep report access private from a child who does not know it, not to resist offline guessing if a recovery file is copied. Existing passphrase-protected vaults remain readable. The overall application remains experimental and is not ready for real-family monitoring.

## Implemented experiment

A writer with a parent public key can seal an individual JSON event using PyNaCl's libsodium sealed boxes; only the matching private key can decrypt it. Payloads are padded to one of several fixed-size buckets before encryption. A record's bucket is visible and leaks an approximate plaintext length. Earlier 4 KiB-padded records remain readable. The encrypted agent table stores a row identifier, a coarse expiry day and ciphertext, not event fields, precise timestamps, application names or interface names. It is tested for wrong-key rejection, modified ciphertext, oversized records and the absence of test values in database files after closing. The library, underlying platform and integration must receive security review before making security claims.

## Remaining design decisions and risks

- **Pairing and custody:** the prototype can generate the private key on the parent device and serve only its public key through a five-minute, one-use pinned-TLS transfer. Initial setup and report return display a two-digit nearby code; a UDP discovery response maps it to the corresponding pinned-TLS endpoint. The short value is not authentication: a device on the same LAN can guess it or observe the discovery response. Network traffic can expose only the public key or a report database that is already encrypted to the parent's private key. The child setup validates the certificate pin before receiving the typed key and showing the installation disclosure. The parent dashboard requires the parent to download the encrypted vault and confirm it was stored before releasing a child setup key; this is an explicit reminder, not proof that the file was safely stored. Local-network discovery and its firewall/privacy prompts have not been validated on Mac or Windows and may fail on networks that block broadcasts. The parent dashboard can also export a typed public-key file after the backup reminder is completed. New vaults use Argon2id (three operations, 64 MiB) and libsodium SecretBox with a six-digit PIN chosen by the parent. An offline attacker can try all six-digit PINs against a copied vault; this is not a strong boundary against someone who obtains the backup. Existing passphrase-protected vaults remain readable. The dashboard clears the in-memory key after 15 minutes without protected activity and stops an active key transfer when explicitly locked. A fresh parent install can restore the encrypted vault backup with its PIN or older passphrase, but it does not yet provide OS-protected storage, recovery if the PIN is lost, revocation or rotation. Loss of every usable encrypted copy of the key or its PIN means loss of access to the encrypted reports; the software has no master recovery key.
- **Leakage:** SQLite file existence, record count, record ordering, per-record expiry day, key fingerprint, file growth and filesystem timestamps remain visible. Size buckets do not hide those facts and reveal approximate record size. Operating-system swap, crash dumps, backups, logs, and the process's memory can contain sensitive data. A compromised or privileged child's machine can observe data before encryption and alter the program or public key. The optional browser channel uses a same-user Unix socket; it does not authenticate the sender, and domains exist in process memory before encryption. The Mac installer creates a random 32-byte device key in the private Ruffster data folder for HMAC router hints; this key is not the parent's encryption key. Router hints are pseudonymous, not anonymous: the key and candidate router hardware addresses can enable guessing. Raw router addresses are not stored. Parent-set network labels are stored separately in an encrypted file.
- **Parent dashboard access:** the local dashboard binds to IPv4 loopback, uses a one-use launcher token and an `HttpOnly`, `SameSite=Strict` session cookie, and checks the host plus browser origin metadata for API requests. These checks help prevent a different local web page from reading reports through the browser; they do not protect against another process running as the same user or someone with administrator access.
- **Integrity:** Sealed boxes detect ciphertext modification, but anyone who has the public key can create a valid new encrypted event. They do not prove which process wrote an event or detect deletion, reordering, replay or replacement of the database. Do not call these tamper-proof or a complete audit trail. Source authentication and anti-replay/rollback need a separate threat model and independent design.
- **Retention:** the experimental agent keeps an unencrypted expiration day alongside each encrypted record to support autonomous deletion without the private key. For a fixed retention setting, that reveals approximately which UTC day an observation was recorded. Expiry is bounded by the configured maximum; day rounding may remove an event up to a day earlier. The agent prunes on startup and while it runs, so an event can remain past expiry while the computer or agent is stopped. Existing databases made with the earlier one-day-later expiry are adjusted once by changing only their expiry metadata; ciphertext is not rewritten. Parent-side retention also prunes incoming reports when imported or opened, or immediately when shortened. Exported backups are outside those retention controls. Secure deletion from backups, snapshots or physical storage is not guaranteed. This tradeoff needs review before production.
- **Migration:** the agent no longer writes new plaintext activity. A developer-only `encrypt-legacy` command can convert the known plaintext activity schema into a new parent-key-encrypted database. It opens the source read-only, validates the schema and event fields, retains data according to original timestamps, creates the output exclusively, and leaves the source untouched. This does not convert arbitrary databases, erase the source, or guarantee secure deletion from SSDs, backups or snapshots. Verify the encrypted output before deciding whether to delete the original. The encrypted dashboard reconstructs its report in memory, but operating-system swap, crash dumps and browser behavior remain outside this guarantee. Never put the parent private key on the child's computer.
- **Local transfer:** experimental one-time transfers use TLS, a short-lived bearer token, and an exact certificate fingerprint. The client checks the pin before sending the token. A report transfer returns only a sanitized encrypted SQLite snapshot. Parent setup can separately serve the typed public key over the same pinned, one-use model; it never sends the private key or encrypted parent vault. The two-digit UI code resolves to the internal endpoint metadata over local UDP. It is intentionally easy to share and is not secret; someone on the same local network can enumerate it. The transfer works only on the same local network, is not persistent pairing or remote access, and has not had an independent protocol review. A substituted discovery response is rejected by the certificate pin unless the sender intentionally shares a different code.

References: [libsodium sealed boxes](https://doc.libsodium.org/public-key_cryptography/sealed_boxes), [PyNaCl public-key encryption](https://pynacl.readthedocs.io/en/latest/public/).
